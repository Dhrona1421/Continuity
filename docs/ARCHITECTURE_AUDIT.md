## Actual lifecycle (not a promise of full automation)

1. **Telemetry → security event.** Authenticated `POST /api/v1/events` accepts `EventCreate`; `POST /events/telemetry/{sysmon|suricata|zeek|cowrie}` normalizes source payloads (`backend/app/api/routes.py:189-235`, `backend/app/connectors/telemetry.py:17-113`). `ingest_event` remaps API names, deduplicates by `event_id`, persists and commits before detection (`backend/app/services/ingestion.py:13-33`). The route best-effort indexes in OpenSearch and records `EVENT_INGEST` audit (`backend/app/api/routes.py:196-213`). Authorized web requests use a separate allowlisted entrypoint (`backend/app/api/web_security.py:72-110`), sanitize/redact and create a normalized event (`backend/app/services/web_detection.py:368-433`). The web path also publishes SSE notifications (`backend/app/api/web_security.py:81-89,483-515`).
2. **Detection → alert.** Startup syncs local rules and web rules (`backend/app/main.py:29-39`; `backend/app/services/detection.py:55-88`). The Sigma-compatible matcher supports named selections with simple `and`/`or` and equality/contains/prefix/suffix, not arbitrary Sigma (`backend/app/services/detection.py:40-52,91-130`). Matching rules produce uniquely fingerprinted `Alert`s with rule confidence, severity, ATT&CK technique IDs and event evidence reference (`backend/app/services/detection.py:133-164`). The web path detects signatures/behavior/authorized upstream signals, groups 15-minute `AttackDetection`s and attaches alerts (`backend/app/services/web_detection.py:137-195,255-365`). No alert is created for an unmatched normalized event.
3. **Alert → correlation → incident → risk.** Normal alerts group on host (fallback source IP/domain/hash), first technique (fallback rule ID), and a four-hour time bucket (`backend/app/services/correlation.py:44-51`). `correlate_alert` creates/joins an incident, attaches the alert, deduplicates IOCs extracted from event IP/domain/URL/hash, appends `INCIDENT_CREATED` or `ALERT_CORRELATED` to the timeline, and stores deterministic risk score/level/reasons (`backend/app/services/correlation.py:54-113`). Web incidents instead correlate source + target in a four-hour bucket (`backend/app/services/web_detection.py`, `_incident_for_web_attack` and `_upsert_attack`, around lines 230-365). Risk is highest alert severity × 0.55 + highest alert confidence × 25 + up to 10 for additional alerts + up to 20 for malicious IOCs, capped at 100; thresholds 35/60/80 determine MEDIUM/HIGH/CRITICAL (`backend/app/services/correlation.py:11-41`). IOC enrichment can mark malicious and recalculate risk (`backend/app/api/routes.py:698-737`). This is deterministic scoring, not ML.
4. **Investigation.** `GET /incidents/{id}` loads alerts, IOCs, evidence, timeline and actions together and sorts timeline (`backend/app/api/routes.py:74-81,631-643`). ATT&CK IDs come from rule tags or web definitions on alerts, with a curated lookup for display (`backend/app/services/detection.py:31-37`, `backend/app/mitre.py:6-91`, `backend/app/api/routes.py:380-402`). `POST /incidents/{id}/evidence` requires `RUN_INVESTIGATION` (`backend/app/api/routes.py:685-695`); `collect_evidence` requires an authorized target, rejects unsupported non-demo collection, and in demo mode creates explicitly attributed **mock** endpoint/YARA/network evidence with hashed details and an `EVIDENCE_COLLECTED` timeline entry (`backend/app/services/investigation.py:15-67`). There is no free-form hypothesis, root-cause or analyst investigation-step model yet. Web attack evidence is also kept as aggregate JSON on `AttackDetection` (`backend/app/models.py:150-175`), not automatically a separate `Evidence` row. `GET /timeline` and `/iocs` provide cross-incident listing (`backend/app/api/routes.py:334-377`). Incident graph and broader visualizations are read-only projections (`backend/app/api/visualizations.py:52-610`).
5. **Response → approval/policy → action → audit.** `GET /incidents/{id}/response-context` derives allowed typed actions, targets and permission flags from the incident and active policy (`backend/app/api/routes.py:433-554`). `POST /response-actions` requires `EXECUTE_RESPONSE`; `POST /response-actions/{id}/approval` requires `APPROVE_RESPONSE` (`backend/app/api/routes.py:784-816`). The seeded policy preapproves `COLLECT_EVIDENCE` and `RATE_LIMIT_SOURCE`, and requires approval for `QUARANTINE_FILE`, `TERMINATE_PROCESS`, `BLOCK_IOC`, `BLOCK_SOURCE`, `ISOLATE_ENDPOINT` (`backend/app/core/bootstrap.py:14-52`). `create_action` validates allowlisted action and policy/risk/authorized target, reserves idempotency key, leaves approval-required actions pending, appends timeline and audit, and commits (`backend/app/services/response.py:17-46,62-150`). `decide_action` requires an undecided pending action, records approver, reason, outcome, timeline and audit (`backend/app/services/response.py:153-203`). **Destructive typed actions are human-approval-gated by the seeded Safe default policy; do not weaken this.** Current code's gate is policy-data-driven: a differently configured policy's `preapproved_actions` can take precedence over `require_approval_actions` (`response.py:94-95`), so future integrations must never assume that every possible custom policy enforces the seed's approval list. No real response adapter is implemented: dry-run explicitly records `executed=false`, while non-dry-run without an adapter records `FAILED`, not real containment (`response.py:49-59,117-128,162-180`). No `DISABLE_ACCOUNT`/`REVOKE_SESSIONS` action exists; examples in later prompts cannot be portrayed as existing executable actions. `record_audit` stores structured actor/target/result/details (`backend/app/services/audit.py:8-35`); audit covers key API operations but is not a universal journal of every ORM write.
6. **Resolution → reporting.** `PATCH /incidents/{id}` permits status/owner updates (including `RESOLVED` and `CLOSED`), appends `INCIDENT_UPDATED` timeline and audit (`backend/app/schemas.py:9-18,196-199`; `backend/app/api/routes.py:646-682`). There is **no** validated transition state machine, closure outcome/root-cause record, or automatic lesson extraction. `POST /incidents/{id}/reports/{pdf|json|csv|zip}` builds exports from persisted incident, web attack and response records, stores report hash/metadata and audits generation; download is a separately authorized path (`backend/app/services/reporting.py:22-115,117-233`; `backend/app/api/routes.py:835-885`). ZIP contains incident, timeline, IOCs, ATT&CK mapping and evidence *metadata/references*, not proof of collected raw forensic files (`backend/app/services/reporting.py:174-195`).

## Part 2–4 integration boundaries (proposed, **not implemented**)

1. **Memory lifecycle.** Create a dedicated adapter in `backend/app/services/hindsight.py` (file does **not** exist yet), configured via `backend/app/core/config.py:20-59` and `.env.example`/`docker-compose.yml:47-90`. The two incident creation paths to observe are `backend/app/services/correlation.py:69-113` and `backend/app/services/web_detection.py:255-365` (including updates to an existing web attack); their DB commits should not wait on memory availability. Closure is handled at `backend/app/api/routes.py:646-682`, but **no outcome exists**: Part 2 needs an explicit, authorized outcome/lesson recording contract before retaining an experience; do not infer success from CLOSED or from DRY_RUN. Actual response result/decision is committed in `backend/app/services/response.py:62-150,153-203`; this is a natural outcome signal, but do not call a simulated action a successful containment. Consider durable, idempotent retry/outbox semantics; simply making an external network call inside a DB transaction can lose events or block the SOC. External telemetry and recalled content are untrusted prompt inputs; reject uncited historical claims.
3. **Incident UI.** Extend the existing `IncidentDetail` at `frontend/src/App.jsx:107-135`, mounted after selection in `App.jsx:137-150`; keep Summary/Attack graph/Evidence & IOCs/Timeline/Response & audit intact (`App.jsx:118-133`). ### Future memory API sketch (paper only)

Use the existing `/api/v1` prefix, e.g. `POST /api/v1/memory/retain`, `/recall`, `/learn`, `/update`. Require `RUN_INVESTIGATION` or `MANAGE_INCIDENTS` for authoring, `VIEW_EVENTS` for incident-scoped recall, and server-side authorization to the referenced incident; do not expose a provider credential. Proposed requests/responses:

- **retain:** `{incident_id, outcome_id, experience: {incident, investigation, response, lessons, analyst_feedback}, idempotency_key}` → `{status: retained|unavailable, memory_id?, incident_id}`. Snapshot references to real incident/alert/evidence/action IDs, attack/technique context, outcome and verified success/failure plus reasons; require explicit provenance for analyst-authored text. No unsupported inferred history.
- **recall:** `{incident_id, limit}` → `{status: available|unavailable, matches: [{memory_id, source_incident_id, relevance?, experience, provenance}]}`. Exclude the current incident, scope to organization, bound limit and use provider-supported relevance; zero matches must mean no relevant historical experience, not invented material.
- **learn:** `{incident_id, recommendation_id?, decision: accepted|modified|rejected, reason, modification?, outcome?, lesson?}` → `{status, memory_id?}`. Preserve rejection and failure with at least the richness of acceptance and success; an accepted *recommendation* is not evidence of successful execution.
- **update:** `{memory_id, expected_version?, annotation, correction_reason}` → `{status, memory_id?, version?}`; keep audit of actor, original provenance and revision. Prevent arbitrary cross-incident mutation.

The exact Hindsight SDK/HTTP contract and availability semantics must be checked against the actual provider in Part 2. Do **not** invent retain/recall scores, project-internal memory IDs or success claims before implementation. Future configuration slots (not added here): provider URL, tenant/bank identifier, credential secret, connect/read timeouts, enabled flag, with production validation and Compose pass-through; avoid logging credentials. The current `Settings` uses `GHOSTSOC_` prefix, `.env`, CSV validators and cached reads (`backend/app/core/config.py:11-21,61-91`); example variables are in `.env.example:1-48`. Compose passes explicit environment variables instead of auto-passing every `.env` value, so Part 2 must update both. Missing/failed Hindsight must be represented as `unavailable`, never a fabricated empty history. Existing `.env` handling, secrets/authorization and dry-run controls remain unchanged.
