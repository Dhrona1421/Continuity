# Hindsight memory layer (Part 2)

GhostSOC calls Hindsight's documented `POST /v1/default/banks/{bank_id}/memories` (synchronous `items` with stable `document_id`) and `POST .../memories/recall` (`query`/`budget`). Hindsight performs fact extraction and multi-strategy recall; PostgreSQL only stores a structured, auditable **source experience/provenance projection** linked to the existing incident ID. A PostgreSQL row **cannot** be recalled alone: Hindsight must return its document ID and the row must be `RETAINED`. No local JSON file or OpenSearch index impersonates Hindsight. [Provider API](https://hindsight.vectorize.io/developer/api/quickstart), [retain](https://hindsight.vectorize.io/developer/api/retain), [recall](https://hindsight.vectorize.io/developer/api/recall).

`backend/app/services/hindsight.py` constructs a redacted snapshot from real `Incident` relationships; `backend/app/models.py:MemoryExperience` stores document ID, status, version, and these five categories. `incident`: ID, title, severity, risk/reasons, techniques, alert/IOC/evidence/timeline references, optional analyst-authored root cause/outcome. `investigation`: hypothesis, steps, successful/failed paths, important evidence, reasoning. `response`: typed actions, approval/execution (DRY_RUN is **not** success), verified successes, failures, side effects, result. `lessons`: analyst-authored `{lesson, condition, recommended_behavior, confidence, source_incident}` (untrusted client fields; verify provenance against incident when extending). `analyst_feedback`: decision, reason, modification/outcome, analyst ID, optional lesson. A failed investigation/response and rejection are retained just like success. Avoid raw event payloads and provider credentials; URL indicators have userinfo, query and fragment stripped before retention. Analysts must still review any sensitive free-text evidence/notes before sending them to a provider. Keep separate banks per organization; bank ID is server configured.

APIs: `POST /api/v1/memory/retain` (incident ID + explicit outcome/hypothesis/lessons), `/recall` (incident ID + 1–10 limit), `/learn` (accepted/modified/rejected, reason, optional outcome/lesson), `/update` (memory ID, expected version, correction). `GET /api/v1/incidents/{id}/experience` reads the **current incident's own source record** and provider status; it does not imply that Hindsight recalled it or that this case is historical. `retain` and `update` require `MANAGE_INCIDENTS`; `learn` requires `RUN_INVESTIGATION`; `recall` requires `VIEW_EVENTS`; all check real incident existence. Writes audit actions; version conflict is returned without overwriting. `learn` and `update` re-retain the same provider document ID, which Hindsight upserts. Closure at `routes.py:update_incident` and approval decisions at `routes.py:response_approval` trigger retain after the existing DB commit. Recall happens when incident view calls the memory API, not on every ingestion. Explicit failures leave a local `UNAVAILABLE` status and are not presented as historical recall. A retry of retain is possible through the endpoint; resubmitting the same analyst decision retries without duplicating its feedback entry. Explicit retain/learn requests default to a configurable 60 s timeout for synchronous provider fact extraction; the incidental closure/approval hooks use a shorter 3 s timeout to bound their response latency. These network calls still block their own requests, and a durable automatic outbox is not implemented; revisit for higher-throughput deployments.

`POST /api/v1/memory/search` accepts a query and limit and calls Hindsight recall directly. It displays only facts returned by Hindsight; a source incident is attached only when the returned document ID matches a `RETAINED` source record. Unmatched World Facts and other results remain visible with an explicit unlinked label. The incident recommendation path is stricter: it uses only provenance-matched historical experiences. Access requires `VIEW_EVENTS`.

Configure `GHOSTSOC_HINDSIGHT_URL`, `GHOSTSOC_HINDSIGHT_API_KEY`, `GHOSTSOC_HINDSIGHT_BANK_ID`, `GHOSTSOC_HINDSIGHT_TIMEOUT_SECONDS` using `.env` (see `.env.example` and Compose backend passthrough). Unconfigured/HTTP/timeout/invalid response returns `unavailable` without blocking incident creation, closure or investigation. Optional Compose `memory` profile starts a Hindsight container with persistent storage; set `GHOSTSOC_HINDSIGHT_URL=http://hindsight:8888` and a working `HINDSIGHT_API_LLM_API_KEY` in a private `.env`, then `docker compose --profile memory up -d`. A key and running provider are **required** for real fact extraction; an empty configuration never supplies synthetic memory. The default Compose stack still runs without memory and visibly degrades.

`backend/tests/test_memory_layer.py` exercises the actual GhostSOC API and Hindsight REST request/response shapes with an **in-process HTTP contract emulator**, including all four operations, unrelated cases and unavailable behavior. These tests prove application wiring, **not** live retrieval quality or actual LLM fact extraction. On 2026-09-28, the separate seven-case live run against Hindsight Cloud and Groq verified retain, recall, source provenance, no-memory comparison, analyst acceptance/rejection feedback, conflict reasoning, and changed later recommendations across the three synthetic NovaBank incidents. The seven live checks all passed; this is functional evidence on one synthetic scenario, not a production-quality or accuracy benchmark. Do not label emulator results as live-provider verification.
